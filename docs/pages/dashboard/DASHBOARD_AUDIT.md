## Архитектура и уже работающие части

- `/app` открывает защищённый workspace; dashboard подключён к общему shell и использует role-specific API. Основные точки frontend: `frontend/src/components/workspace/shell/WorkspaceShellView.tsx`, `frontend/src/components/workspace/shell/hooks/useWorkspaceShellController.ts` и `frontend/src/components/workspace/panels/MainFeedPanelView.tsx`.
- Backend dashboard использует авторизованные role-specific endpoint-ы в `backend/Api/Controllers/DashboardController.cs`; Applicant query читает сохранённые связи откликов и время первого просмотра. Данные не следует заменять frontend seed-ами.
- Для Customer shortlist отображает серверные псевдонимы: `backend/Application/Candidates/GetVacancyCandidates/GetVacancyCandidatesQueryHandler.cs` формирует имя с учётом роли. Это важная граница приватности и должна сохраниться при любых UI-изменениях.
- Исполнитель уже получил отдельную секцию с выбором проекта, краткой сводкой и фильтрами Pool/Shortlist/Selected (`frontend/src/components/workspace/panels/ExecutorDashboardSection.tsx`). Существуют loading/error/empty/retry состояния и общий dashboard shell.
- Заказчик уже видит данные кошелька и shortlist по выбранной вакансии; выбор заказа открывает существующую страницу деталей. Для кандидатов существует API выбора финалиста и frontend RTK endpoint.
- Соискатель уже видит реальные отклики и доступные статусы/времена из dashboard API в `ApplicantApplicationsSection.tsx`; vacancy discovery, подача отклика и просмотр резюме реализованы отдельно.
- Дизайн-токены, Tailwind и строгие frontend DTO уже существуют. Новая параллельная UI-система не нужна.

## Baseline-проверки (до изменений)

- Backend: `dotnetdevmcp` build `backend/Api/Api.csproj` — успешно, 0 ошибок, 0 предупреждений.
- Frontend: `npm run build` — успешно (TypeScript + Vite, 2016 модулей). Сохранились предупреждения о Browserslist/caniuse-lite старше 8 месяцев, bundle более 500 kB и времени Vite plugins.
- Frontend tests: `npm run test:run -- --reporter=dot` — 40 passed, 4 failed из 44 тестов (1 из 14 файлов). Все четыре падения находятся в `src/components/workspace/panels/MainFeedPanel.test.tsx`: неоднозначный поиск повторяющегося статуса «В работе»; assertion на устаревший CSS-класс Customer row; ожидание старого текста Applicant empty state; Applicant проверка вкладки «Архив», которой нет в текущем разделе откликов. Это исходные падения до правок в рамках данного аудита; их тестовые контракты нужно сверить с текущими требованиями, а не маскировать.
- Backend tests: обнаружено 52 integration tests. Прогон дал 10 passed и 42 failed из-за `Npgsql` authentication failure для настроенного пользователя БД `neondb_owner`; тестовое приложение не может подключиться к текущей БД. Конфигурацию и данные БД не менял. Dashboard-specific integration tests среди обнаруженных тестов отсутствуют.
- Browser: runtime-сравнение недоступно. Просмотрены только исходные `screen.png` и HTML-макеты.

## Последовательный план исправлений

1. Зафиксировать этот аудит и план; оставить несвязанные файлы нетронутыми.
2. Executor: подключить безопасное действие смены Pool/Shortlist в существующей dashboard-панели; проверить роль, выбранную вакансию, loading/error и обновление списка.
3. Customer: подключить существующий выбор финалиста; проверить, что данные кандидатов остаются псевдонимными для заказчика.
4. Applicant: улучшить выбранный отклик на основании доступных API/маршрутов; не выдумывать interview invitation, историю или расписание.
5. Устранить ложное подтверждение доставки чата и проверить состояние календаря без источника встреч.
6. Проверить адаптивность и доступность изменённых экранов; браузерные проверки выполнить только если browser runtime доступен.
7. Запустить относящиеся тесты после каждого этапа и полную регрессию в конце; отдельно зафиксировать DB/browser ограничения.
8. Удалять только подтверждённые неиспользуемые файлы; `dashboard-app/` автоматически не удалять.

## Критерий закрытия

Каждый экран должен использовать реальные role-scoped данные, показывать только поддержанные действия, сохранять privacy-политику Customer и проходить доступные сборки и релевантные тесты. Любое отличие от макета из-за отсутствующей доменной модели/API или недоступного браузера должно оставаться явно задокументированным; сборка сама по себе не считается доказательством визуальной готовности.
