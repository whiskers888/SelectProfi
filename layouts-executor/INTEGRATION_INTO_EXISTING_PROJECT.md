## Жёсткие правила

1. Не копировать `src/main.tsx`, `src/App.tsx`, `package.json`, `yarn.lock`, `vite.config.ts`, `tsconfig*`, `src/index.css` из MagicPath поверх существующего проекта.
2. Не копировать корневой `AGENTS.md` из этого архива поверх инструкций репозитория. Этот архив — **справочный источник**, не новый корень проекта.
3. Не монтировать MagicPath как отдельный `iframe`, вложенное Vite-приложение или всю React-оболочку через `dangerouslySetInnerHTML` в рабочем кабинете. Это демо-реализация для извлечения UI/UX, а не production-код.
4. Не переопределять глобальные `window.*`, не переносить inline `onclick` и глобальные CSS-правила из выгрузки в приложение. Перевести действия на React-обработчики, локальные компоненты и существующие модель/API-слои.
5. Не переписывать существующие компоненты «с нуля» без причины и не удалять работающую бизнес-логику. Сначала сопоставить существующее и нужное, затем править небольшими диффами.
6. **Визуальная цель — 1:1 с MagicPath.** Сохранять сетку, плотность элементов, типографику, границы, интервалы, тексты и интерактивные состояния, но выражать цвета/стили с использованием существующих дизайн-токенов `tokens.json`, Tailwind и компонентов `components/ui`.
7. Текущий `CLAUDE.md` и работающие API-контракты имеют приоритет над демологикой MagicPath. Не превращать mock-состояние и примерные суммы в настоящую бизнес-логику.
8. Учитывать права: заказчик видит кандидатов только в разрешённых состояниях, доступ к контактам — только по текущим правилам приложения. Не переносить переключатель демо-роли как обход авторизации.
9. Термин в пользовательском UI: **«Список кандидатов»**. Во внутренних моделях и существующем API `Shortlist` можно оставить, чтобы не нарушить контракт.
10. Сохранять адаптивность, light/dark темы, клавиатурную навигацию, focus-visible и WCAG 2.2 AA.

## Этапы реализации

### Этап A — аудит и карта соответствия (кратко, не останавливаться на нём)
- Проверить `git status`, текущую ветку, работающие экраны/путь `/app`.
- Изучить исходники MagicPath, особенно `renderPoolV3`, `renderAddCandidateV5`, `renderResponsesV4`, `renderJobV4` и CSS последних переопределений.
- Сопоставить с существующими panel-компонентами, не добавлять дублей.
- Зафиксировать: что уже совпадает, что отличается, какие реальные API есть, какие элементы демонстрационные.

### Этап B — кандидатский сценарий (начать с него)
- Привести `CandidatesSection.tsx` и `CandidateCreatePagePanel.tsx` к виду MagicPath.
- «Добавить кандидата» открывает **полноценную страницу**, а не модальное окно; хлебные крошки: `Мои проекты в работе / З-1039 · Менеджер по продажам B2B / Добавить кандидата` (в реальном продукте из реальных данных).
- Вкладки: `Из своей базы`, `Из откликов`, `Загрузить резюме`. Сохранять доступные рабочие действия и состояние в существующем приложении.
- Боковое меню на широком экране не прыгает и не сужается при входе/выходе со страницы; базовая ширина по референсу около **224 px**. Мобильная компоновка адаптивна.
- Разделять **«Кандидаты проекта»** и **«Список кандидатов для заказчика»**. Отправленный список нельзя тихо перезаписать или удалить.
- К каждому кандидату в рабочем проекте добавить понятное действие `Удалить` с модальным подтверждением и обновлением счётчиков/истории. Прежде чем подключать реальную операцию — проверить, существует ли корректный API и что он означает («отвязать от вакансии» vs «удалить профиль»). Если API нет — явно зафиксировать контракт/блокер; не имитировать успех как серверную операцию.
- Для опыта работы сделать общую функцию склонения (`1 год`, `2 года`, `3 года`, `4 года`, `5 лет`, `11 лет`, `21 год`, `22 года`) и покрыть тестами. Проверить все карточки, отклики, фильтры и подробные профили.

### Этап C — остальные интерфейсные модули
- Карточка заказа: `Кандидаты / Отклики / Требования вакансии / Моя вакансия / История / Документы / Оплата` с сохранением существующих прав и backend-контрактов.
- «Отклики»: поиск, кнопка `Фильтры`, фильтры в модальном окне, сброс/применение, статусы.
- «Требования вакансии» — данные заказчика без незаметной перезаписи. «Моя вакансия» — отдельный черновик текста рекрутера; в UI возможен экспорт TXT и печать в PDF, внутренние заметки не попадают в публичный экспорт.
- «История», «Документы», «Оплата», чат: перенести визуальный дизайн и существующие рабочие сценарии, не хардкодить фиктивные платежи, статусы или мнимые действия.
- Разбивать работу на проверяемые самостоятельные коммиты/части, а не переделывать всё за один проход.

### Этап D — проверка
Из каталога `frontend/`:
```bash
npm ci
npm run tokens:build
npm run build
npm run lint
npm run test:run
```
Проверить вручную в браузере desktop (например, 1440 px) и мобильную ширину (около 390 px): навигацию, кандидатов, добавление тремя способами, удаление, отклики, смену роли/прав, историю и возврат назад. При необходимости добавить UI-тесты на хлебные крошки, табы, подтверждение удаления, счётчики и склонение стажа.
